When we started the migration, the plan fit on one page and said two weeks. We had four repositories, one shared library copied between them, and a CI setup that took forty minutes on a good day. Moving everything into one repository was supposed to halve that.

It did, eventually. Build time went from 41 minutes to 9. But the first three weeks after the move were slower than anything before it, and the reason is worth writing down.

## What we moved

The four repositories became four packages under one root. None of the code changed in the first pass.

<Table caption="The packages after the move." source="Measured on main, 1 September 2026">

| Package  | Lines of code | Tests | Depends on     |
| -------- | ------------: | ----: | -------------- |
| `web`    |        48,200 | 1,130 | `api`, `shared` |
| `api`    |        31,900 |   860 | `shared`       |
| `shared` |         9,400 |   410 | none           |
| `infra`  |         6,100 |    95 | `shared`       |

</Table>

## Why everything got slower

Our cache keys were built from the hash of the whole repository. In four small repositories that was fine. In one big repository it meant any change, anywhere, invalidated every cache.[^cache]

I want to tell this part from my side. For most of that week, every morning started with a red pipeline and a Slack thread asking whether it was safe to merge. It usually was. The pipeline was red because it had run every test in the company for a one-line README change.

</Signed>

## Teaching CI the graph

The fix was to let CI ask the workspace which packages a change touches, then run only those packages and the ones that depend on them.

<Terminal title="~/work/monorepo">

```shellsession
$ npm run affected -- --base=origin/main
> Changed files: packages/shared/src/date.ts
> Affected packages: shared, api, web, infra
$ npm run affected -- --base=origin/main --only=infra
> Affected packages: infra
```

</Terminal>

The function behind that command is short. Most of the work is in agreeing on what "affected" means.

<CodeBlock title="scripts/affected.ts" href="https://github.com/oykucann/the-blog">

```ts
export function affected(changed: string[], graph: Map<string, string[]>): Set<string> {
  const result = new Set<string>();
  const queue = changed.map(packageOf);

  while (queue.length > 0) {
    const pkg = queue.shift()!;
    if (result.has(pkg)) continue;
    result.add(pkg);
    for (const [dependent, deps] of graph) {
      if (deps.includes(pkg)) queue.push(dependent);
    }
  }
  return result;
}
```

</CodeBlock>

<Details summary="Why we walk dependents and not dependencies">

A change in `shared` can break `web`, because `web` imports it. A change in `web` cannot break `shared`. So from each changed package we follow the arrows backwards, to the packages that import it.

This is the same rule most build tools use.[^tools] We wrote our own because the script is 20 lines and we wanted to read every one of them.

</Details>

The pipeline was never broken. It was doing exactly what we told it to.

## What we would do differently

Write the dependency graph first, before moving a single file. Then the move is only a move.

<Note type="tip">
If you are planning a similar migration, measure your CI time for two weeks before you start. Without that baseline you cannot tell whether the move helped.
</Note>

<Quote by="Fred Brooks" source="The Mythical Man-Month" href="https://en.wikipedia.org/wiki/The_Mythical_Man-Month">
Adding manpower to a late software project makes it later.
</Quote>

We did not add people. We added a graph, and that was enough.
